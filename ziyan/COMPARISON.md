## 7. 口径与限制

- 老库默认 `query` 同时索引正文与描述；自衍中枢只索引 name/description/tags。第 3 节的“老描述基线”用 description+tags 的 token 重叠做对照，避免把“少了正文索引”误读成“描述检索变差”。
- 老库存储统计只复制了 `knowledge/`；自衍中枢包含 `files/` 与 `system/`（DB、快照、设置、日志）。文件数差异主要来自每实体一个目录 + meta.json + SQLite。
- 写入计时是 API 路径（不含 fsync）；启动计时是热缓存下的单次调用；Node 26 环境，桌面端 Node 24 的绝对数值会更高，两侧同环境对比仍成立。
- 迁移把老附件变成了独立文件实体，并补了卡片 ↔ 附件的 links；所以自衍中枢的图比老图多节点/边，这是模型差异，不是排序 bug。
- 样本是 135 张卡 / 10 个附件的真实库；延迟绝对值很小，受机器负载影响；大库趋势需另测。

## 8. 结论

- 描述检索：新库 top5 与老库“描述基线 top5”重合 19/32；差额来自排序策略（基线是 token 重叠，自衍中枢是 BM25+新近度+度数）和附件文件进入 top5。老库默认（正文+描述）top5 共 40 条，比描述基线多 8 条，那是正文索引的额外召回。新库返回体平均 2890.25 B，老库 5311.13 B（老查询结果带正文）。
- 正文词检索：accessible 1→0；active 1→0；agents 1→4。2/3 个新库 0 命中，说明“描述没写就搜不到”；其余是附件描述/迁移描述带来的新命中。
- 注入：老 3450 B，新 3041 B，差 -409 B。
- 存储：老 18 个文件 / 361046 B；新 292 个文件 / 682914 B（189.15%）。新增主要是每实体的 meta.json、DB 与快照。
- 写入：老 12.55 ms / 100，新 70.7 ms / 100；新库每次写字节+边车+DB 三处，老库是一次追加日志。
- 启动：老库首次加载 10.06 ms；新库重开 0.49 ms、全量重建 23.87 ms（空库首次打开 6.16 ms，不可比）。
- 图：老返回 13 节点 / 20 边；新返回 37 节点 / 50 边，新库把附件也当成节点。
