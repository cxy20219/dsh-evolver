# 会变的东西不进系统段：注入层拆成「静态纪律 + 运行时候选」

## 问题

系统提示（`systemPrompt.section`）参与请求前缀缓存：任何一次改动都会让整条对话的缓存前缀作废，
写一张卡的成本从「复用缓存」变成「全量重算」。早期把整个标签树放进系统提示，结果每新增一个枝干、
每补一句说明，都要重写整段系统提示——一次写卡让整段缓存失效。

## 做法

| 部分 | 载体 | 变的频率 |
|---|---|---|
| 纪律 + 工具指针 + 主动性协议（`CARD_DISCIPLINE` + `CARD_INDEX_POINTER` + `PROACTIVE_PROTOCOL`） | `systemPrompt.section`（order 900，合成一段） | 只随代码发布变 |
| **卡片索引 + 结构摘要**（`cardIndexText`） | `systemPrompt.context`（order 900） | 每日快照，写卡不改 |

两段静态内容合成一个 section：两者都是常量，拆成两个只会多一个块边界和一次 `order` 排序，
合并后的文本与「两段用 `\n\n` 连接」逐字节相同（提示词装配器 `renderPrompt` 就是丢弃空段后用 `\n\n`
连接各 section 的）。代价是这一段占住 order 900：以后若有 section 的 order 落在 900–920 之间，
它会排到主动性协议后面（DSH 内置顺序表里 900 之后紧邻的是 1000，当前没有冲突）。

关键点：运行时的那半**只读快照**（`knowledge/index.json`）。快照有两个写入时机：

1. **每日整理**写完一批后重写（内容没变就不写文件）；
2. **每次打开数据目录**（首次启动、迁移、导入、切换）都先建一次——新库没有快照，若不在这里建，
   第一个请求就要在全库上现排序。也就是说「打开即快照」把回退成本挪出了请求路径。

于是「写卡」这条最高频路径不会改动注入文本（当天快照已存在时）；新枝干/新卡片只会等下一次
整理进入快照。

（历史：这一层最初是标签树，2026-11-12 换成「关系最多的卡片 + 一段结构摘要」——树只回答
「怎么分类」，索引才回答「先读什么」。当时实测标签树迁到 runtime context 后，新增枝干的未缓存
输入从 29 万 token 降到 651；现在换成卡片索引，注入体积约 2 KB 且写卡零改动。）

## 数字（真实库实测：95 张卡时 1366 B，113 张卡时 2191 B）

- 静态系统段：纪律 1003 B + 主动性协议 1020 B = 2025 B（合成一段，与拆两段逐字节相同）；
- 注入索引：2171 B（12 张卡：10 枢纽 + 2 张最近写的，短 id + 结构摘要），预算 4096 B；静态段 1274 B（纪律 430 + 主动性 844）；合计约 1076 token/请求；
- 旧全量标签树：约 1.2 KB，但只有分类、没有可读入口；
- 写卡后注入文本字节不变（当天快照未刷新），只有整理运行或重新打开数据目录才更新快照。
- 回退路径（快照缺失/过期）本身要排序全库，所以必须记忆化：真实 95 卡从 0.25 ms 降到 0.013–0.022 ms；
  合成 2000 卡无快照从 43.8 ms 降到 3.3–4.3 ms（按 store 版本 + 当天缓存，命中 0.04 ms）。
  不记忆化时，这个成本会挂在每一次请求上。

## 边界

- 快照缺失/过期/损坏 → 回退实时排序（`topCardsOf`），不报错；此时写卡会改变注入（首日或坏文件修复期），
  因为记忆化键含 store 版本，写卡会让缓存失效一次。
- 快照写入必须原子（临时文件 + rename），且内容相同不重写——否则每日空跑的 tick 会每 10 分钟改一次文件。
- 注入文本绝不做隐式写盘：`cardIndexText` 只读，写快照只在整理流程与「打开数据目录」时发生。
- 新增会随数据变化的内容时，先问它属于哪一半：进 `systemPrompt.section` 就必须接受一次写卡让整段
  前缀失效；进 `systemPrompt.context` 则必须有一个不随写卡变化的快照来源。
