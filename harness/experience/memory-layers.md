# 记忆分层：三层 + 检索，而不是四层

> 本文是**当前实现**的记录。历史：曾对齐 Anthropic《The components of agent memory》做过「枝干页」表示层
> （`kind:'page'`、`pages.json`、每日页维护），2026-11-12 用户决定整体移除——页对人和对模型的边际收益
> 都不如把搜索做好。移除记录见 git 历史与 README。

## 现在的分层

| 层 | 演化器里的东西 | 谁维护 |
|---|---|---|
| 会话记录 | 宿主会话日志 + `session_digest` | 宿主 |
| 笔记 | 卡片（`id` + `description` 就是一张卡的全部身份：**没有标题**，`links` 是双链，`source` 带出处与会话 id） | agent / 会话整理 |
| 资源 | 面板「资源」顶层页只读聚合（卡片右边）；存储仍是卡片附件：正文里出现附件路径就算「引用」，所以一个文件可能被多张卡用，点「看引用它的卡片」跳的是按路径过滤的列表。预览按类型分流：文本/图片/PDF 在面板里渲染（文本 >200 KB 截断），其余交给系统程序打开（宿主 `open`/`xdg-open`，路径由 store 从卡片 id + 文件名解析，客户端从不传路径）；`knowledge/resources/<卡片id>/<文件名>`，正文用 `[标题]({{resource}})` 引用；脚本自动 chmod +x，`card_read` 给绝对路径，`card_query` 结果带 `resources`（名字 + 是否可执行） | 写卡时带 resourceName/resourceContent |
| 注入 | 纪律（静态 section）+ **卡片索引**（运行时 context：12 张卡 + 结构摘要） | 每日整理写 `knowledge/index.json`；打开/迁移/导入数据目录时也建一次；请求只读 |
| 检索 | BM25 词法命中 + 沿双链扩散的关系图（`card_query graph:true` / `within`） | 每次查询时算，无快照 |
| dreaming | 每日整理：批次复查 → 死链修复 → 快照重写 | 插件 |

**没有表示层（wiki 页）。** 那一层的职能被两件事分摊：注入里的「关系最多的卡片」承担入口，
检索里的「双链扩散」承担从入口走到关联卡。对我们这种百张卡、问题多为「找到那条规则」的库，
这比给每个枝干养一张页更划算。

## 注入为什么是卡片索引 + 摘要

旧注入是全量标签树：它随枝干增长而变长，却只回答「知识怎么分类」，不回答「最该先读什么」。
新注入两块：

1. **12 张卡**：每行 `短 id｜描述`。**卡片没有标题**——正文第一行是散文，曾经被当成标题切进索引，
   结果是每行都以一句被截断的话开头（2026-11-13 按用户要求去掉，只留 id 和描述）。短 id 是 ULID 的唯一后缀（5–8 字符），
   `card_read`/`card_write`/`card_query within` 都接受它（唯一才解析，撞了报错）；完整 31 字符 id 仍是存储与链接的权威。
   关系数用和检索同一套无向双链度，所以索引指向的正是搜索会走到的枢纽。
   **位置怎么分**（2026-11-13）：10 个给枢纽，2 个给最近写/改过的卡。排序键依次是
   度数 → `access.json` 里的读取次数 → 更新时间 → id：度数管结构，读次数只在同度数时翻盘
   （没人打开的老枢纽仍然算枢纽，但平手时被真正在用的卡顶掉），时间与 id 保证两次运行结果一致。
   老规则「只看度数」的问题是：一张今天刚写、还没链的卡永远进不来，索引永远指向同一批老枢纽。
2. **知识结构摘要**：一段话，只有六个枝干的总数（`共 118 张卡，按枝干：践行 42 · 见闻 27 · …`）。整理器每天可以写一版更好的
   （整理回复里的 `summary` 字段），没写就用确定性兜底。

收益（真实库实测：**注入索引快照 3084 B / 预算 4096**，静态段 1383 B，合计约 1100 token/请求）（短 id 比完整 id 省 ~210 B），旧全量树 1.2 KB 但只有结构、没有可读入口；更重要的是
**写卡不再改注入**——索引读每日快照，快照内容没变就不重写文件，请求前缀不受写卡影响。快照有两个写入
时机：每日整理，以及每次打开数据目录（首次启动/迁移/导入/切换）——新库若不在打开时建快照，第一个请求
就要在全库上现排序。

## 检索为什么是「词法 + 图」

- 词法（BM25 + 只按最近访问的 recency 生命周期加权 + MMR）负责「说到了这些词的卡」；没有 rerank hook，
  唯一的候选打分就是词法 + 图扩散；
- 图扩散负责「关于同一件事、但没说到这些词的卡」：
  种子按词法分归一化，每跳 ×0.55，加 `1 + 0.35·ln(1+度)` 的枢纽加成，多种子共同指向的节点被加强；
- `combine = min(1, 词法 + 0.7 × 关系)`：词法主导，关系只补位，不会把纯邻居排到命中之前；
- 一次调用返回 `cards + related + graph` 子图，`within` 可在子图里做二次搜索。

不引 embedding：这套库上实测 embedding 只改变排序、不改变召回（见 `src/memory/hybrid.js` 顶部注释），
双链是库自己维护的数据，扩散就是它的回报。

## 边界

- 注入的体积上限由构造保证（12 张卡 + 一段话），但仍受 `DEFAULT_PROMPT_BUDGET` 保护：超预算先丢描述、
  再减卡片行，摘要永远保留；最后一级兜底按**字节**截（`clipToBytes`），不按字符——`String#slice` 数的是
  UTF-16 单元，中文会被切出三倍预算。
- **注入去重，不是少说**（2026-11-13）：卡片纪律原来有 7 条，其中 5 条和 `card_write` 的工具描述逐字重复——工具描述每轮也在请求里，等于同一段文字付两遍钱。现在纪律段只留工具没说的（六枝干与三层的规则、`#即兴` 收件箱、查重、密钥筛查都在工具描述里），从 424 字压到 194 字；主动性协议同法从 434 字压到 354 字；摘要去掉六个枝干括号里的解释（它们本身就是中文词，`card_index` 里带描述）。合计 **1480 → 1076 token/请求（-27%）**，删掉的内容模型一格工具描述就能看到。（2026-11-13 项目级落点改写后主动性协议 425 字，静态段 1383 B。）
- **字段上限不是行宽，是"还有没有意义"的界线**（2026-11-13）：描述上限 80，
  再小就是在重切作者写好的标题；且截断一律在标点处收尾并加 `…`（`clipField`）。早先是 44 字硬切，
  本库 61/113 张卡的标题超过 44 字，于是索引里一半的行都是"…的 Cookies ｜连 5"这种断口，
  既花了字节又什么也没说。字段上限只放在 `injection-index.js` 一处，渲染层不再二次裁。
- **没有描述的行只剩短 id**（2026-11-13）：去掉标题后，`description` 成了索引唯一的信息载体。
  本库 113 张卡里只有 6 张写了描述，于是 12 行里 10 行只有 id、注入从 2191 B 掉到 1009 B（后来补全了 118 张）。
  这不是渲染 bug，是内容缺口；已补齐 107 张（平均 60 字，全库 113/113 有描述）。
- **描述是必填项，且不许是占位词**（2026-11-13）：`assertRealDescription` 在 `card_write` 与
  HTTP `card-write` 两个入口执行——空、`暂无`/`TODO` 这类占位词、少于 4 字、超过上限一律拒绝并说明原因，
  不再"先写进去再说"。上限由设置 `cardDescriptionMaxChars` 决定（默认 80，夹在 20–200），
  同一份值同时管**存储写入**与**索引渲染**（`descriptionCapOf`），两处不再各写一个数。
  会话整理落下的卡由正文按标点裁剪生成描述（`clipDescription`），所以自动路径也不会留空。
- 12 张是容量选择：8 张只点名 113 张里的 7%，且每天都是同一批；12 张 + 2 个新鲜位置，代价约 +380 B/轮。
- 快照缺失/过期/损坏时回退实时排序（`topCardsOf`），不报错；回退按 store 版本 + 当天记忆化
  （真实 95 卡 0.25 ms → 0.013–0.022 ms；2000 卡无快照 43.8 ms → 3.3–4.3 ms，命中 0.04 ms），
  所以「首日/坏文件」不会把全库排序挂到每次请求上。
- `knowledge/access.json` 由访问账自己 flush 写（30 秒间隔 / 20 次变化 / 关闭时），每日整理只读它做
  批次降权，不写。
- `evolve_review` 的 `index.ratio` = 注入索引字节 / 正文字节，超过 10% 提示索引大过内容。
- 页移除后，`kind` 字段与 `pages.json` 都不再存在；旧库里的页卡会按普通卡参与检索，不报错。
