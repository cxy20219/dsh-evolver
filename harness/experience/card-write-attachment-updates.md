# 附件更新语义：同名替换、改名归档、死链降级

## 触发数据

2026-11-13 全天会话扫描：插件工具共 140 次调用，`card_write` 42 次里有 13 次失败（31.0%），其中 5 次与附件有关、1 次与死链有关。一个真实失败链（dsh-manager 会话）连续 4 次被拒：

1. 更新已有卡时漏 `description` → 拒绝；
2. 补描述后同名附件被「同名附件已存在」拒绝；
3. 改成新文件名后，旧附件仍躺在卡目录里 → 「正文必须引用附件 <旧名>」拒绝；
4. 再试 `{{resource}}` 时又变成「未解析占位符」。

根因不是模型笨：旧规则同时要求「新增附件不得同名覆盖」和「卡目录里每个文件都必须被正文引用」，却没有任何删除/改名入口；一旦有人想更新附件，这张卡就进入死锁。

## 现在的规则

- `CardStore.put(input, { replaceResources })`：只有调用方显式传入才允许替换；且只放行**大小写完全一致**的同名文件（净化和大小写碰撞仍拒绝，避免 `a b.md` / `a-b.md` 静默互盖）。
- 替换前把旧文件**复制**到 `knowledge/trash-resources/<card-id>.<时间戳>/`；新内容写失败时旧文件仍在原位。
- 更新已有卡时，正文不再引用的旧附件**移动**进回收站，不再让整次写入失败；`card_write` 结果用 `warnings` 点名被归档的文件。新增附件仍必须被正文引用（写卡契约不放松）。
- `card_write` 的 agent 路径在 `id` 存在时传 `replaceResources: true`；面板 `card-attach` 仍保持「新增」语义，不传该选项。
- 链接目标不存在时 agent 跳过该边并在结果 `warnings` 中说明，卡片正文照常保存；`CardStore.put` 的显式死链仍是硬错误（直接调用方不能静默丢边）。
- 正文超限错误带上当前字数，便于一次改对。

## 量化（同一失败序列，HEAD vs 工作区）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 同 id 同名附件原地替换 | 拒绝 | 成功，旧档 v1 在回收站 |
| 改名附件（旧名不再引用） | 拒绝 | 成功，旧档 v2 在回收站 |
| 死链卡片写入 | 拒绝 | 成功，`warnings: 1` |
| 50 次同名替换 | 0 成功 / 50 拒绝 | 50 成功 / 0 拒绝 |
| 200 次普通更新 | 24 ms | 23 ms |

按今日观测口径，13 次失败中 5 次可由这套语义消除：31.0% → 约 19.0%（剩余为正文超限、描述缺失/超长、未解析占位符等契约性拒绝）。

## 守卫

- `test/cards.test.mjs`「card_write 更新附件：同名替换留旧档、改名自动归档、死链降级为警告」覆盖三条路径与回收站内容。
- 既有「附件同名不覆盖」测试保留：`attach` 不传 `replaceResources`，净化同名与大小写同名仍拒绝。
- 既有「显式写入的死链接仍然报错」测试保留：降级只发生在 agent 工具层，存储层不静默丢边。
