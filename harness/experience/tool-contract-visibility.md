# 工具描述是能力的第一现场

## 现象

用户在另一个项目里反馈：「harness 写入的时候只能整体写入，不够灵活」。把那次的会话记录（`session.v4.jsonl.zstd`，zstdcat 解压后按 `tool/call` / `tool/result` 配对）还原出来，真实动作是：

1. `file_edit` 改 harness 里的手册 → 报「只能改 harness/harness.md 或四层内的资源」；
2. `file_write` 带**整篇 content**（4835 字节）重写同一份手册 → 报「只能写 harness/harness.md 或四层…」；
3. 改用 `bash` + python 字符串替换**绕过插件**改成了；
4. 后来用 `mv` 把文件从 `harness/` 根挪进四层，但**没补描述边车**，根 `AGENTS.md` 仍是手写文档、里面索引的路径已失效。

一次「加一条规则」走了 4 次插件调用（2 次失败）+ 2 次 bash 绕过 + 2 次全文读。

## 根因

**能力已经存在，只是描述没说出来。** `file_edit` 对 harness 资源**早已支持 `old`+`new` 精确替换**（改写正文 → 重建索引 → 校验 → 失败回滚），测试也覆盖着。可工具描述把「正文替换」只说给库文件与项目文件，harness 那句写的是「*还能*用 meta.description/meta.title 改它的描述边车」——模型读成「harness 资源只能改描述和标题」，于是选错了动词。

第二个根因是**约束没给出路**：位置不在四层时，报错只陈述限制、不说下一步。模型的理性选择就是自己发明旁路，而**旁路必然破坏契约**：没有描述边车、索引与目录不一致，下次正式写入会被校验判错并整体回滚。

## 做法

1. **先查工具描述，再查实现**。模型只能看到描述；描述没写的能力对它等于不存在。改能力时同步改描述，并把「目标 × 能力」矩阵写进去（库文件 / 项目文件 / harness 资源各能用哪些动词与参数）。
2. **避开排他措辞**。「还能用」「只做」会让模型推断出比真实边界更窄的能力范围；宁可写「都适用」。
3. **报错给下一步动作**，不要只陈述限制（「把它移到 `harness/<层>/` 下再写一次」），否则模型会去自创旁路。
4. **约束不放松**。根下多余条目仍报校验错误——有明确通路时一次就能清掉，放松只会让 harness 长期停在「一半被管、一半没人管」的状态。
5. **旁路一律按契约破坏处理**：改完补边车、重建索引，否则下一次正式写入必被回滚。
6. **看真实会话的工具调用链**（`~/.dsh/sessions/**/session.v4.jsonl.zstd`），比看对话文本更能定位「模型为什么选错动词」。
