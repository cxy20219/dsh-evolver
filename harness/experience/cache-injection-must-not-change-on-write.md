# 注入块里的计数，是每次写卡都付一次的全量重读

> 这份记录纠正了它自己的前一版。前一版把一天里的缓存缺口归给"换模型"，
> 加上归因能力后重新对账，发现 22 次里有 20 次是注入块本身。

## 现象

一天 556M prompt token、1686 条助手消息，命中率 **97.5%**。
22 次缓存全丢，代价 7.87M，占总量 **1.4%**。

未命中的时间分布：**12:00–15:26 密集 20 次**，另有 21:14 和次日 08:23 各一次。

## 第一版结论（错的）

当时看间隔：每次未命中前都有 `system/message`，而系统提示里写着
`powered by the <model> model`，于是判断"模型在来回切，换一次模型就作废一次前缀"。

问题在于**只看了模型名在不在变**，没有看系统提示的正文差在哪。

## 真正的原因

把 12–15 点那 20 条系统提示逐条比对，模型名全程都是 `deepseek-v4.1-flash`，
变的是**标签树的计数**：

```diff
- #践行/演化器 (2)
+ #践行/演化器 (2) — 让演化器自身持续改进的机制与记录
```

那一版注入的树带 `(n)` 计数。写一张卡 → 计数变 → 系统段变 → 前缀作废 →
下一次请求把几十万 token 的对话重读一遍。

提交 `f443f5d`（11-11 14:54）去掉计数后，这类未命中停止。
所以这条不是"外部原因"，是**插件自己造成的，也是插件自己修掉的**。

## 做法

1. 注入块只放**与写操作无关**的内容：标签路径、描述、纪律。
   任何"写一张卡就会变"的数字都不能进系统段。
2. `cache_report` 给每次未命中附归因（`model-switch` / `system-section` /
   `resume` / `expired` / `tools`），并给出计数分布。归因要沿着**整条时间线**
   追踪模型名——回退只写一条系统消息，它自己说不出"我换了"。
3. 判据只剩一条：`system-section` 占比高，就是注入块又带上了易变内容。

## 边界

- 一次重启（`resume`）必然全量重读一次，这是会话恢复的固有成本，不算异常。
- 宿主不记录 `cacheWriteTokens`（实测全为 0），`prompt = input + cacheRead`。
- 会话日志是 `session.v4.jsonl.zstd`，**多帧拼接**；Node 的 `zstdDecompressSync`
  只解第一帧，要按魔数 `28 B5 2F FD` 切帧逐个解。
- 命中率有天然上限：每轮新增输入必然未命中，40 万 token 的会话约 98%。
  所以看 `misses` 与 `byCause`，不要盯命中率的小数点。

## 验证

```
cache_report
```

成功信号：`byCause` 里 `system-section` 为 0，`recent.misses` 为 0。
失败信号：`system-section` 抬头——回去看注入块，一定又混进了随写操作变化的数字。
