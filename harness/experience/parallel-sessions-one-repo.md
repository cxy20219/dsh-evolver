# 同一仓库并行会话的认知分叉

## 现象

同一个仓库开了两个会话做同一条工作线。后开的那个会话拿到的是**自己启动时刻的快照**：更早的提交历史、更旧的源码、更旧的未提交改动。等它动手时，另一个会话可能已经把同一件事做完并提交了。

实际发生过一次：自衍中枢的「项目 AGENTS.md 变成生成的索引 + 描述进边车 + 旧布局迁移」被拆到两个会话。会话 A 走完全程并提交；会话 B 的上下文停在更早的决策点（还在讨论索引格式该长什么样），它按旧认知继续给方案、改文档。结果仓库里同时留着两套认知的痕迹：会话 B 描述的模型已经不是仓库里的模型，而会话 A 最后一步（静态提示词改动）留在未提交状态——下一个会话无法判断那些改动属于谁、想干什么。

## 根因

- 会话上下文是**时点快照**，不是共享状态。两条会话线之间没有「当前真值」的通道。
- 摘要里的「已提交 / 未提交 / 工作区干净」是**线索**，不是事实；事实只能从工作区读。
- 共用一份工作区 = 共用一个可写状态，两个会话的写操作之间没有任何仲裁。

## 做法

1. **开工先对齐事实**，不要相信摘要里的状态描述：

   ```bash
   git log --oneline -5
   git status --short
   ```

   还要读一遍准备改的那个文件的当前内容——它可能已经被另一个会话改了。

2. **并行必须物理隔离**：`git worktree add ../<repo>-<topic> <branch>`，每个会话一份工作区、一条分支，要合流时再合并。共一份工作区的两个会话必然互相覆盖。

3. **同一个文件只留一个写者**：两个会话都要改同一个文件时，要么串行，要么后一个先读最新版本再改。

4. **收尾必须留痕**：要么提交（message 写清做了什么、为什么这么做），要么在答复里明确列出「未提交的文件 + 属于哪次改动 + 为什么没提交」。含糊的「我改了一些东西」等于没有交接。

5. **交接用提交和差异，不用散文**：下一棒需要的是 `git log` + `git diff`，不是「我做了什么」的叙述。

## 边界

- 这条经验解决的是「两个会话同时改一个仓库」的协调问题，不解决「两个会话改同一个文件」的合并冲突——那仍然要靠分支合并和人工判断。
- 摘要是压缩过的上下文，只能用来定位线索，不能用来断言状态。
- 判断改动归属时，先看 `git log` 与 `git diff`，再看时间戳；时间戳只能当参考。
