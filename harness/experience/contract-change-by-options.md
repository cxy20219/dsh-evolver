# 契约与提示词改动：先给选项，再动手

## 现象

用户对提示词、注入段、工具契约这类改动的要求很明确：**「先把优化前后的给我过一遍，不要直接修改」「我选完你再改」**。实际推进下来的固定形态是：给现状诊断 + 两到四个完整候选 + 体积对比表 → 用户回一个字母 → 一次改到位（源码、测试断言、文档、测试结果、生效方式）。

## 根因

提示词和契约改的是**模型行为**，不是代码正确性。「加了这句话模型会怎么变」这件事，用户的判断比 agent 准。直接改等于把决策成本转成返工：改完了用户发现方向不对，前面的代码、测试、文档一起白做。

## 做法

1. **不动文件，先给四样东西**：
   - 现状原文（完整贴出来，让人能对照）；
   - 问题诊断落到结构，不是措辞：重复、与工具描述重复、职责混装、长度预算——这些比「这句读着别扭」值钱；
   - 两到四个**完整可替换**的候选（不是「这里加一句」的增量说明，用户要能整段替换）；
   - 量化对比：字节数、估算 token、相对增减，一行一项，配推荐。
2. **结尾给明确指令**：让用户回复 `A / B / C`，不要让用户在长文本里自己找。
3. **用户拍板后一次改到位**：改源码 → 同步受影响的测试断言 → 同步文档（README / DESIGN / AGENTS）→ 跑测试 → 报告生效方式（宿主侧改动要不要重启 DSH）。
4. **把「不确定但影响取舍」的地方留在方案里说清楚**，不要替用户做主；但也不要为了显得周全而列一堆明显不行的选项——两三个真正有取舍的更好。

## 边界

- 纯 bug 修复、拼写、格式、注释这类没有取舍的事情**不要**走这套流程，直接改、直接报。那是在浪费对方的注意力。
- 只有「多种做法都说得通」时才给选项；只有一种明显对的解法时，把方案和理由一起说清楚即可。
- 选项之间要有真实差异（有取舍），不要把同一个思路换三种措辞。
