# 载荷要能被对方解析：截断与类型声明

## 现象

插件的自主整理引擎跑了 80 次作业，10 次成功但**全部 0 写入**；同期的工具调用里还有 5 次库写入因 `meta.tags 必须是数组` 失败、4 次因 `file_edit 没有可执行的操作` 失败——失败方都没法自纠。

## 根因（两个，都出在"边界没写清"）

**一、字节流截断砍断了结构。** 工具结果按字符切到 8000：`file_search` 返回 10,410 字符，模型收到的是 `{"total":28,"files":[{"schema":1,"id":"file-01M7…`——半个对象。解析不了就换词重搜，把预算烧在检索上，永远走不到写。日志吻合：25 次工具调用、处理 2/5 个会话、0 写入。

**二、schema 没声明类型，模型就自己发明格式。** `meta` 是 `additionalProperties: true` 的自由对象，`tags` 没说是数组，于是部分路由输出 `{"item": ["来源/harness"]}`。**同批调用里声明了 `type: 'array'` 的 `file_search.tags` 一次都没错过**——这就是根因证据。

## 做法

1. **能声明类型就声明，不要在运行时解包。** 解包是给「本不该发生的错误」做兼容层；schema 声明能让它不发生。代价是常驻 token（本例 +159 tok），比一次失败调用加它的重试便宜。
2. **截断要按结构切，不要在字符上切。** 丢整个数组元素、保留标量字段，再补 `truncated` / `omitted` 交代丢了多少——尤其要留住 `total` 这类"一共有多少"的字段，否则模型无法判断看到的是不是全部。
3. **报错要点名对方实际发的是什么。** 「没有可执行的操作」让模型原样重试 4 次；「这次收到的是 new_string，应该用 old 和 new」一次就纠正。报错文案不在 schema 里，常驻成本为零。
4. **调参前先修根因。** 作业预算是够不够，要等截断修好、再跑一次真实作业才判得准；在根因没修时调预算只是把症状挪个位置。

## 边界

- 只对**结构化载荷**（JSON 结果、工具返回值）要求可解析；纯文本消息（日志、结论文本）用字符截断没问题。
- 「声明类型」不等于「加校验」：类型声明是给生成方的提示，运行时校验该留还得留。
- 兼容层只在**无法控制上游**时才做；上游是本仓库定义的 schema，改 schema 就是治本。

## 验证

- 断言「超限结果裁剪后仍是合法 JSON 且带 `truncated`」——比对字符串长度更本质。
- 断言「schema 里 `tags.type === 'array'`」——把类型声明变成契约，防止以后被人删掉。
- 用**真实数据**复现：同一份 10,410 字符的检索结果，裁剪后 7,985 字符、可解析、保留 15/20 条。
