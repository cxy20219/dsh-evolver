# 缓存命中率不归注入块管，归模型选择管

## 现象

一天下来 556M prompt token、1675 条助手消息，命中率 **97.52%**。
21 次缓存全丢，代价 7.87M token，占总量 **1.41%**。

直觉上会怀疑是插件注入的东西在变。查下来不是。

## 数据

未命中集中在两个窗口：

| 时间 | 次数 | 当时在发生什么 |
|---|---|---|
| 12:00–15:26 | 20 | 提供方回退：31 条 `llm/retry`，系统提示被重写 27 次，模型在 `MiniMax-M3.1-Flash` 与 `deepseek-v4.1-flash` 之间来回 |
| 21:14 | 1 | 宿主重启，会话在新进程里恢复 |

模型稳定之后（21:14 起）126 条消息，命中率 **99.05%**。

## 根因

系统提示里嵌着**模型名**（`powered by the <model> model`）。模型一换，
整段系统提示就是一串新字节，前缀作废，模型要把几十万 token 的对话重读一遍。

这不是插件的注入块，是**模型选择**。

另外两个候选原因都被排除了：

- **写卡**：注入树不带计数，往已有枝干写卡不改变一个字节（实测两次渲染指纹相同）
- **写 harness**：项目指令更新走的是 `user/message` 事件，是**追加**而不是重写系统提示，
  所以对前缀没有任何影响

## 做法

1. 会话语义层面能做的只有一件事：**别在同一会话里换模型**。提供方不稳定时宁可换会话，
   也别让回退在长会话里反复触发。
2. 插件层面：把数字做出来。`cache_report` 读当前会话的 `assistant/message.usage`，
   给出命中率、未命中的步数、以及这些步的代价（`missCost` / `missShare`）。
   未命中的判据是 `cacheRead === 0`——首条不算，之后每条读到 0 都是前缀被重建。

## 边界

- 宿主**不记录** `cacheWriteTokens`（实测全为 0），所以 `prompt = input + cacheRead`。
  命中率分母用这个和，与 `totalTokens − outputTokens` 一致。
- 一次重启必然产生一次全量重读，这是会话恢复的固有成本，不算异常。
- 会话日志是 `session.v4.jsonl.zstd`，**多帧拼接**，Node 的 `zstdDecompressSync`
  只解第一帧；要按 zstd 魔数 `28 B5 2F FD` 切帧逐个解。

## 验证

```bash
# 插件内
cache_report        # 当前会话的命中率与未命中代价
```

成功信号：模型稳定时命中率 > 99%，`missShare` < 2%。
失败信号：`missShare` 明显上升，且 `misses` 里出现相隔十几秒的连续未命中——
那说明系统提示在会话中途被反复重写，去看是不是在切模型。
