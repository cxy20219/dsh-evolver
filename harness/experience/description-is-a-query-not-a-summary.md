# 描述是预判的查询，不是内容的摘要

## 现象

库里的描述一直是「写清它是什么 + 以后哪些场景会用到它」。用户提出疑问：正文如果能被检索到，描述还有必要吗？会不会过时？是不是只对二进制文件有意义？

## 根因

描述被当成了两件事：**准入门槛**（不写就不让存）和**检索入口**（FTS 只索引 name 与 description，正文完全没进）。一个字段承担两职，写得不好就找不到，改过正文就脱节。

## 判断

描述的本质既不是摘要也不是门槛，而是**预判的检索查询**——用「你以后会搜的字」写「什么时候会需要它」。

实测依据：库里 166 条描述与正文的双字组合重合率中位数 74%，即约 26% 的词正文没有。那 26% 正是「排查时先…」「给 X 定方案前读」这类**未来时态的意图词**——正文永远不会有，因为正文写的是「我当时在做什么」。

模板套话（「按附件文档/可复用步骤」）占 5%，它们既不是摘要也不是查询，是纯噪音。

## 做法

1. **正文进索引**，但权重压得很低（bm25：描述 10、名字 6、正文 2）。描述命中 = 「这篇就是关于你的问题」；正文命中 = 「词在里面出现过」。
2. **正文只取头部**（32 KB），二进制不索引——描述本来就是它们唯一入口。
3. **描述口径改成「什么时候用」**：「是什么」正文已经能搜到，重复它没有收益。
4. **描述仍然必填**。覆盖率 100% 说明成本付得起；放开只会换检索质量下降。

## 边界

- 「正文进索引」≠「搜索返回正文」。返回的仍是描述，所以**渐进式披露的结构不变**：先看描述决定要不要读全文。
- 拉开权重不是为了排序好看，是为了防退化：如果正文权重接近描述，「反正搜得到，描述随便写」很快就会发生。
- 长描述（≥30 字）通常自带触发条件（现象、前提、错误），不必强制塞场景词；短描述必须有点场景。

## 验证

- 单测：两篇文件都含同一个词，描述命中的排在正文命中的前面。
- 真实库副本：挑「描述里没有、正文里有」的词检索，3/3 命中目标文件。
- 重建成本：165 个文件 25 ms（正文只在扫描时读头部）。
