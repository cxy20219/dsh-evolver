# 标签治理：动作、纪律、护栏三件套

## 适用场景

改每日卡片整理（`src/consolidate.js`）、注入的标签纪律（`src/cards/prompt.js` 的 `CARD_DISCIPLINE`）或标签守则（`src/cards/tag-policy.js`）时。

## 根因：规则没有动作入口，说什么都白说

2026-11 之前，整理器系统提示词第 4 条写着「归类：把标签收敛到正确的枝干」，但动作只有 `delete / update / merge`，**改标签只能走 `update`**；而同一段提示词又把 `update` 限定成「只在改写正文时用」。于是按规则办事的模型，唯一合规行为就是**不碰标签**。

真实数据的症状：

- 97 张活跃卡里 39 张仍带 `#即兴`，但**其中 38 张已经有落定枝干** —— 归枝做了，收件箱标签从来没人摘；
- `tags.json` 不存在，所有枝干说明都来自代码常量，新枝干天然是裸路径；
- 一次性枝干（`践行/缓存实验分支` 这类测试残留）没有被回收的机制；
- 没有动作审计，改提示词无法评估。

另外三处文字互相矛盾：整理器说「不超过两层」（当时），注入段说「整理时选一个枝干继续向下生长」，`card_write` 工具描述说「子标签自由向下生长」。

## 现在的结构

### 1. 动作（src/consolidate.js）

新增两个动作，补齐语言：

```json
{"op":"retag","id":"卡片id","tags":["标签"],"reason":"#即兴 → #践行/经验"}
{"op":"tag-merge","from":"旧子枝干","to":"新枝干","reason":"两个枝干是同一件事"}
```

- `retag` **只写 tags**，正文一字不动；`update` 保持「改写正文」的语义。这是整次改造的关键：没有它，提示词写什么都落不了地。
- `tag-merge` 是唯一允许动批外卡片的动作（它按定义要改全库）：只合并**子枝干**，拒绝顶层枝干和 `#即兴`，一次运行最多一个，说明跟着搬走。
  应用是「先收集、后写」：要改的卡全部收集并校验完才动第一张，写到一半失败不会把库拆在两个枝干上却不知道停在哪；
  单卡写入失败只跳过该卡并记审计，不阻断其余卡。
- 回复可以带 `descriptions` 根字段：`{"actions":[...],"descriptions":{"践行/工具":"一句说明"}}`。

### 2. 纪律（提示词）

整理器系统提示词现在明写：每张超过 14 天的卡必须落定；已落定的摘掉 `#即兴`；先复用后新建；一次最多一个新枝干；新枝干必须带说明；命名规则；最多三层（枝干/主题/子题）；归档不写；现有枝干不改名，近义用 `tag-merge`。卡片块里加了 `创建: YYYY-MM-DD`，年龄规则才有依据。

注入段（`CARD_DISCIPLINE`）把「继续向下生长」换成「先复用再新建 + 落定后摘掉 #即兴 + 三层 + 中文命名」，`card_write` 工具描述同步改掉。静态段改动只失效一次前缀缓存。

### 3. 护栏（src/cards/tag-policy.js）

提示词管不住的部分由代码兜底，四条按顺序生效：

1. `归档` 是状态不是分类 —— 整理写 `<枝干>/归档` 一律丢掉（否则一张卡会被悄悄归档，不进回收站，也再不出现在整理批次里）。
2. 枝干最多三层（枝干/主题/子题）。判定用的是**归一化之前的原始路径**——否则 `normalizeTag` 会把四层静默截成三层，等于替模型做了一次决定。
3. 一次运行最多新建 1 个枝干（`MAX_NEW_BRANCHES`）。
4. 新枝干必须带说明（来自同一回复的 `descriptions`）。

另外两条在 `tagsOf()` 里：超过 14 天的卡不能只剩下 `#即兴`；**被拒的标签只丢标签，不连坐正文改写或合并**（旧实现是 `normalizeCardTags` 抛错，整条动作作废）。

导入/继承来的旧库还可能带着非法顶层标签（例如 `#验证方法`）：写卡与整理写入按**确定性降级**处理——
该标签重挂到 `#即兴` 下（`即兴/验证方法`）并记一条 warning，卡本身照常保存，不会让整轮整理失败。

### 4. 出处：整理器唯一的外部事实

卡片正文证明不了自己有没有记错，所以卡片可以存一句**逐字引用**（`source.quote`，≤160 字），两个来源：
会话提取时模型抄回摘录里的一句原话（抄不到——不在摘录里——就整条出处丢弃），或 agent 用
`card_write` 传 `quote`。编造的出处比没有更糟：整理器会拿一句没人说过的话去"核对"。

整理提示里每张带出处的卡多一行 `原文: 「…」`，纪律是「对得上就一个字别动，对不上按原文改正并在
reason 里写明」。卡片还存 `source.session`（来源会话 id）：整理时按 id 取回引文**前后一段**的摘要
（`readSessionExcerpt`：只留用户与助手的可见文本、抹密钥、截断 600 字、围绕引文取窗口），作为
`出处摘录:` 附在卡上——这就是 dreaming 里 transcript grounding 的最小可用版：不整段回放会话，
但能看到原话所在的上下文，从而判断卡片有没有说反、说过头。
捕获率是可观测的：会话整理的结果带 `quoted`（抄回原文的条数），面板「整理」页会显示
「上次保存 N 条，其中 M 条带得出原文」；卡片详情里也能看到那句原文。

### 5. 审计

删除/合并是「先写副本、再改库」：正文整条先追加到 `knowledge/trash.jsonl`（附件先进 `knowledge/trash-resources/`），
写成功后才 `remove`；写失败时卡片仍在、动作计入 skipped。动作逐条独立（单卡失败不阻断整批），
运行前会检查数据目录是否被迁移/导入换掉、卡片是否在模型调用期间被人工编辑——命中任一条就跳过而不是覆盖。

每条落库动作追加一行到 `knowledge/consolidation.jsonl`：`{at, run, op, id, before, after, reason, dropped}`（跳过的动作不写审计行，只计入本轮 skipped 计数）。`evolve_review` 会回读最近一次运行的摘要（改了几次标签、合并了几个枝干、前几条 reason），`review.tags` 同时给出枝干总数、一次性枝干、无说明枝干、未落定卡数。

## 已知边界

- `tag-merge` 只做精确路径合并，不处理「父枝干带着子枝干一起并」；要并父枝干得先并子枝干。
- 14 天规则只约束 `retag/update/merge` 的 tags，不强制模型必须动；它仍可以整批不动（这是有意的，别把「必须改」写进提示词）。
- 第一次写 `tags.json` 会把代码里的默认说明**物化**成文件条目（读的是有效表、写回整表）；之后手改文件不会丢默认值，但「只写一项」的窄写会丢——所以描述写入必须 read-modify-write。
- `consolidation.jsonl` 只追加不轮转，一年大约几百 KB，可接受；要归档需另做。
- 存储层的 `MAX_TAG_DEPTH` 也是 3（`normalizeTag` 超出就截断），所以四个数字已对齐：存储 3、守则 3、注入段 3、`card_write` 描述 3。导入的老库若真有四层路径，写入时会被截断成三层，读取时仍按原样出现在树里。
