# 混合检索：BM25 召回 + 双链扩散补全

## 问题

卡片搜索原来只有 BM25：它找到「正文里说到这些词」的卡，找不到「和这些卡讲同一件事、但没用这些词」
的卡。卡片库自己维护着双链（`links` + 反链），这正是补充召回的数据，却只被 `card_read neighbors`
用来手动跳转。

## 方案（两段 + 一个子图）

```
query → BM25（取 50 条候选）→ 种子（按最高分归一化成权重）
       → 沿双链扩散（hops 跳、每跳 ×0.55、枢纽加成）
       → combine = min(1, 词法 + 0.7×关系) → 排序 → cards
       → related（不在 cards 里的邻居）+ graph 子图（nodes + edges）
```

- **词法仍是主角**：一条命中卡永远比它两跳外的邻居分高，关系分只用于并列时的重排和补位。
  纯关系命中最高只能拿到 0.7，不会越过强词法命中。
- **扩散**（`src/memory/graph.js`）：从种子出发做有限跳的 BFS 式游走，每跳衰减 `ALPHA=0.55`，
  节点分数再乘 `1 + 0.35·ln(1+度)`——被多个种子同时指到的节点会累加，所以「共同邻居」天然靠前。
- **无向图**：`links` 只存一个方向，但走图时反链也算一条边——指向枢纽的卡与枢纽指向的卡同样相关。
- **死链不进图**：`buildGraph` 只收两端都存在的链接，旧死链不会拉进幽灵节点。
- **子图**（`subgraph`）：只返回两端都在结果集里的边，节点顺序 = 排名顺序，最多 40 个。
- **二次搜索**：`card_query({ within: [id…] })` 先把候选集与 within 取交集，再在同一套流程里检索；
  within 非空时自动进入图模式。用法：粗搜定位 → `graph:true` 看关联 → `within` 在子图里深挖。

## 权重与数字

- `ALPHA = 0.55`、`HUB_BONUS = 0.35`、`combine` 的关系权重 `0.7`、`DEFAULT_HOPS = 2`（工具默认 1）。
- **没有 rerank hook**：唯一的候选打分就是 BM25 + 图扩散。生命周期加权只剩「最近访问的 recency」
  （Weibull 曲线，`0.5 + 0.5·recency`），frequency/intrinsic 两个恒为 0 的项已经删掉，不要再接回来。
- 复杂度 O(种子数 × 平均度数 × 跳数)，百张卡规模下 < 1 ms；不建额外索引，查询时现算。
- 短 id 解析不走「每个 id 全库 filter」：生成快照时按后缀计数（O(N·8)），2000 卡规模下解析从
  44.45 ms 降到 1.52 ms；检索本身的词法 + 扩散在百张卡是亚毫秒级，别让 id 解析喧宾夺主。
- 为什么不用 embedding：本库实测 embedding 只改变排序、不改变召回（90% vs 90%），代价是 592 MB
  与启动停顿；双链是库自己维护的数据，扩散是它的免费回报。
- 为什么不建 GraphRAG 式实体图：那需要额外的实体抽取与社区摘要索引（预处理成本 + 两类缓存失效），
  而卡片本身就是实体节点、`links` 就是边，图已经在库里。

## 测试与边界

- `test/memory-graph.test.mjs`：建图无向/死链丢弃、一跳压过两跳、多种子加强、枢纽加成、子图无悬挂边。
- `test/graph-query.test.mjs`：图模式返回结构与 degree、hops 距离、within 子集、标签/归档过滤、related ≤ 8。
- 普通模式返回形状不变（数组），图模式返回 `{cards, related, graph}`——向后兼容。
- `related` 最多 8 条；`nodes` 里 degree 是候选库内的邻居数，不等于全库入/出链数（后者见卡片视图的 `degree`）。
- 性能回归在 `test/cards.test.mjs`（2000 卡无快照回退的记忆化，`无快照的注入回退按 store 版本记忆化`）
  与 `test/injection-index.test.mjs`（短 id 快照）；短 id 唯一性/冲突报错在 `test/cards.test.mjs`。
